# Discord Rich Presence

Application ID: `1512105518779338843`. Public server: `springplus.net`. Website: `https://forum.springplus.net`.

Presence recognizes the current connected multiplayer session from the existing handshake OR the exact public addresses `springplus.net` / `mc.springplus.net` (default port only, optional DNS trailing dot). This fallback is local to Presence, never changes music/cosmetics authorization, and never matches arbitrary subdomains, IPs, suffixes or other servers. It allows basic server/world/nickname presence even if cosmetic handshake has not arrived; missing privilege/city data is still omitted. Activity requests set the displayed name to `SpringPlus`; the registered application's current name is `Springy`, so clients that ignore the name override need an application-name change in Developer Portal. The bot username is not changed by this mod. Discord URL buttons are visible to other users, not to the activity owner; check with a second account.

Enable in the bell menu: Settings -> Events -> Discord Rich Presence. Presence and every optional field are opt-in. Preferences are local in `config/springplus-discord.properties`; no bot token or OAuth secret is used.

Optional fields: nickname, public privilege name, current city territory, world. The card uses the connected SpringPlus session and the current tab-list count (labelled as tab-list count, not authoritative server population). Other servers never expose these details. Session timer changes when the connection changes. No coordinates, balances, staff actions, private messages, camera information or friend lists are published.

Current territory comes from an optional backwards-compatible Towns extension on the existing towns:ui channel: action 9 with a p-prefixed nonce; reply byte 127, UTF nonce, boolean present, then (when present) UTF name, boolean capital, UTF avatar SHA-256. The server determines ownership from its authoritative chunk marks (including town farm claims), not membership or client coordinates. Status says “В городе <name>” / “В столице <name>”; wilderness omits town information. The mod polls at most once per 3 seconds only while SpringPlus Presence and city visibility are enabled; the server additionally rate-limits requests. No web/API polling is introduced. Chunk/world/connection changes invalidate cached data; mismatched/late nonces are ignored and replies expire after 7 seconds. Old Towns plugins ignore the extension, with no membership-based fallback. Both mod and Towns plugin must be updated for this feature.

**Current user-selected behavior: Site button only**, leading to `https://forum.springplus.net`. The runtime never sends join secrets or party metadata and does not subscribe to join invitations. The old `join=true` preference is ignored and the join toggle/connection confirmation flow is removed. Details/artwork also retain clickable forum links. Live Discord RPC rejected secrets together with URL buttons (5005: secrets cannot currently be sent with buttons), leaving the previous main-menu activity visible; a regression test now prevents this combination. Optional low-level IPC join handling remains only for transport tests/future work, not the active game integration. Closed-game launch/protocol registration is not implemented.

Upload the application image named `springplus` under Discord Developer Portal -> Rich Presence -> Art Assets. When city visibility is enabled and the current territory reply includes an avatar hash, the large image becomes `https://skin.springplus.net/api/chat-images/<sha256>.png`; the small image stays the SpringPlus logo. Missing/invalid hash, no city, a different server or disabled city visibility keeps the default logo and never publishes the city avatar. No additional image download/API poll is performed by the mod. The content hash versions the URL automatically; Discord fetches/caches the public image. This does not test remote image availability or guarantee Discord displays an externally unavailable image. Text remains usable without the application logo. A running desktop Discord is required; browser Discord does not expose the local IPC pipe. The owner may not see their own URL button as another user does.

IPC uses Windows named pipes or Unix-domain sockets on daemon workers, with bounded frames, a 10-second handshake deadline, heartbeats, reconnect attempts, change-only activity updates and best-effort activity clearing on disable. Windows pipe reads first use the JDK's PeekNamedPipe-backed available() check, so an idle blocking read cannot prevent SUBSCRIBE or SET_ACTIVITY from writing on the same synchronous handle. Exact frame reads never issue a zero-byte OS read. Closing a diagnostics-only connection does not clear an activity it never published. There is no new native/JNA dependency. Linux/macOS packaging-specific Discord socket locations may need additional discovery; those platforms are not live-tested.

Pure tests use a fake Discord endpoint: handshake, subscription, activity, fixed-token transport join filtering, clear, privacy and malformed frames. Run `:26.2:checkDiscordPresence :26.2:checkTerritoryPresence -I tests/discord-check.gradle` from Fabric (26.3 on the port). For NeoForge use the corresponding `:neoforge:26.2:` task prefix. Territory checks cover city/capital wording, hidden fields, chunk/world transitions, late replies, wilderness, expiry and avatar bounds. Tests do not publish a real activity, launch Minecraft or contact a server. The territory integration still needs an in-game check with the updated Towns plugin.

This work is local and does not change release versions or deploy. Main Fabric currently embeds the separately fetched WIP InFlow integration; that candidate must not be silently treated as the last production release.
